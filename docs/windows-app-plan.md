# MotionBench Windows 应用分阶段实施方案

本轮先完成冲刺 FVP、能力结构交互及相关回归，保持现有前端、计算和导出链路。Windows 应用随后分阶段实施：先固定模块合同，再包装可运行的桌面程序，然后迁移事务存储，最后处理安装和更新。本方案尚未创建 Windows exe、安装运行时、迁移真实资料或改变浏览器／Windows 安全配置。

## 现有接口作为起点

| 当前模块 | 已有职责 | 桌面化时的接口边界 |
| --- | --- | --- |
| `ringside-fvp.js`／`RingsideFVP` | 跳跃 FVP、最优剖面、弹性与情景计算 | 继续接收测量与配置，返回确定的数值结果；不调用 DOM、文件或资料库 |
| `ringside-sprint-fvp.js`／`RingsideSprintFVP` | 本轮冲刺分段拟合、力／速度／功率、目标距离剖面与原始结构校验 | 保留 `solve/read`、`validate` 及 `METHOD_VERSION`；以最终验收确认具体算法和边界 |
| `RingsideModel.stats()`、`RingsideEvaluation` | 计算和生效评价解析 | 网页、桌面、Excel 与报告消费同一次结果，不在桌面宿主中重写公式 |
| `RingsideModel.capabilityDirections()`、`capabilityDirectionsBasis()` | 四个方向的共享指标与判定，以及 AI 所选依据绑定 | 屏幕、PDF、AI 消费同一投影；所选依据与测量指纹分别绑定，保留旧叙事兼容 |
| `RingsideReport.build()`、PDF 模块 | 报告快照、图表、分页与完整性核对 | 保留现有报告模型和打印布局；宿主只接管保存文件、打印等系统能力 |
| `RingsideStore.Repository` | IndexedDB 事务、目录摘要、记录加载、保存、分代导入和恢复 | 从现有调用面抽取最小存储 adapter，先保留 IndexedDB 实现 |
| `ringside-excel.js`／`ringside-excel-flow.js` | XLSX 模板、解析、预览、采用与一次事务保存 | 文件读写接宿主，字段、单位、稳定 ID、旧模板兼容和保存合同保持统一 |
| `ringside-entry-session.js`、App | 临时录入会话、保存队列和交互 | 会话恢复与长期资料库存储分别管理，未保存草稿不成为已保存记录 |

“最优冲刺 FVP”必须随目标距离、计算方法版本及相应假设保存，不能在桌面化时变成不注明距离的通用标准。图形开关属于显示偏好；四卡所选分析依据另外绑定 AI 草稿，不进入全局测量指纹。原始分段计时、计时起点与测量条件属于记录资料。单位和报告结论继续由模型统一输出。

## 阶段一：计算、存储与备份合同

从现有调用提炼边界，按需要逐个引入 adapter，不更换 UI 框架，也不把所有模块重写为新工程。

存储合同首先覆盖现有 `directory()`、`loadRecord(id)`、`save(lib, records, removals, checks)`、`flush()`、`importRows()`、`createBackupBlob()`、`restorePrevious()` 和 `close()`。保留当前保存前的 `expectedConfig`／`expectedRecords`／`expectedAthletes`／归属全集检查，以及“失败不部分提交”的含义。IndexedDB 和后续本地后端使用同一套合同检查。

2.17.2-local 已在两个真实页面间验证会话与普通记录的完整快照保存检查，并建立可运行的备份一致性、导入激活和恢复并发复现。后续先补一致读取事务与事务内代指针核对，再考虑更换后端；这些未修复项及最小方案见[本轮记录](local-fixes-2.17.2.md)。

备份 codec 与存储 adapter 分开：当前完整库是 schema 3 JSONL，记录 schema 2，Excel 模板 schema 2；三者的版本不能互相替代。备份版本、记录版本、算法版本、应用版本分别记录。新配置用可选字段和明确默认值承接旧记录；新增持久化字段必须经过规范化、保存、备份、再导入和报告验证，不靠 UI 默认值模拟保存成功。

建议增加宿主能力入口，仅包括选择／保存文件、打印、应用路径与凭据调用。浏览器实现使用现有下载与文件输入，桌面实现再提供本地桥接。能力是否可用由 adapter 决定，报告计算不读取宿主种类。

阶段验收条件：

- 原模型回归和新增冲刺数值检查通过，模型可在不启动浏览器时运行。
- 合成记录在两种代表成绩模式下保存、重开、JSONL／JSON／Excel 往返保持测量与配置；旧版本记录继续可读。
- 事务失败、并发预览过期与导入失败保留当前库；恢复前一代不遗漏记录和配置。
- 图表、四卡与参数表在窄屏及实际下载 PDF 中保持同一结果。只有本轮实际执行的检查计入本轮通过项。

## 阶段二：形成真正的桌面程序

获得后续实施与所需工具安装授权后，选定一个宿主做最小可用原型。沿用 `src/` 构建的本地 UI，在应用窗口中运行，生成 Windows 可执行文件和可审查的打包产物。用户从 exe／快捷方式启动，程序负责自身窗口与生命周期，不要求双击 HTML、手动启动 Python 或安装 Node。

| 路径 | 与当前项目的关系 | 选型验证重点 |
| --- | --- | --- |
| Electron | 延续 JavaScript 工具链，并随应用提供 Chromium／Node 运行时 | 现有 Chrome 图表和 PDF 的一致性、程序包体积、更新维护成本、本地桥接 |
| Tauri 2 | 复用同一 Web UI，Windows 使用 WebView2，并引入 Rust 构建工具链 | WebView2 环境及离线分发、现有 SVG／canvas／下载／PDF 行为、团队维护 Rust 桥接的能力 |

建议先比较同一组报告、导入和保存流程的小型原型，再选择维护成本较低的一条路径。最终框架和版本在实施时固定，不同时开发两套正式应用。官方资料说明 [Electron 打包](https://www.electronjs.org/docs/latest/tutorial/tutorial-packaging)、[Tauri Windows 前置条件](https://v2.tauri.app/start/prerequisites/) 和 [Windows 安装包](https://v2.tauri.app/distribute/windows-installer/)；相关运行时或工具尚未在本轮安装。

本地文件和资料库通过有限宿主接口访问。若使用 Electron，渲染器保留隔离和沙箱，禁止直接暴露任意文件／shell 操作，按 [Electron 官方安全文档](https://www.electronjs.org/docs/latest/tutorial/security) 校验桥接调用；不关闭浏览器安全保护以处理 AI 跨域。Tauri 路径同样只授权实际需要的宿主操作。现有 AI 凭据存储能力另作宿主适配，不写入报告、JSONL 或程序资源。

原型先使用独立且稳定的应用资料目录和合成数据。原浏览器资料通过显式 JSONL 导入；不复制浏览器 profile 或假定新应用能直接读取原 IndexedDB。资料库路径与程序安装目录分离，更新程序资源不会移动数据库。

阶段验收条件为：解压／安装后的 exe 在普通用户环境启动和关闭正常、离线录入和导出可用、重启后保存仍在、报告与 PDF 对照一致、Excel 使用原字段合同。原型通过不代表已完成干净 Windows 机器安装验收。

## 阶段三：事务资料库与真实迁移

桌面壳稳定后再引入本地事务存储。优先评估 SQLite；对 UI 保留阶段一 adapter 合同，逐次替换底层实现。程序只读资源与用户数据分开，默认数据目录可采用用户级本地应用目录；同步盘上运行中的数据库需另行验证，不沿用当前源码目录作为默认位置。

本地后端需要保存 athletes、records、recordIndex、groups、profiles、config 和 schema／migration 元信息。每次保存对相关实体与摘要使用一个事务，执行与现有 IndexedDB 相同的并发基线校验。资料库连接由单一宿主协调；数据库与备份文件不能通过一般文件复制冒充一致的事务快照。

每个迁移版本明确 from／to schema、可执行步骤、校验、完成标记及最低可读应用版本。迁移取得版本锁；旧程序不能向已超出其可写版本的数据库继续写入。首次导入先建立独立暂存库，核对条数、ID、归属、方案关联和原始测量后再切换。未完成、空间不足或中断的迁移保留旧库，重新打开时能识别并恢复。

真实迁移前，由用户在原版本、原路径和原浏览器导出完整 JSONL 到本机，核对可读性与完整性，并保留原程序。本轮没有执行这一步。先使用合成数据证明升级与失败回退，再启动真实迁移；迁移后重新导出并核对用户本机资料，不把真实内容作为 Git 测试夹具。

代码与数据分别保留回退点：

- 代码：可执行包、源代码提交／标签、bundle、SHA256 和依赖清单。
- 数据：迁移前完整备份、一致的本地数据库快照、schema 版本与备份校验信息。
- 回退：若旧程序无法读写新 schema，恢复迁移前数据库到独立目录后再运行旧程序。新版本新增资料先导出并保留；不得把降级读不懂的字段静默丢弃。
- 同 schema 的导入回退保留当前分代语义；“恢复导入前”与“恢复升级前”在界面和元信息中区分。

阶段验收覆盖真实进程重启、事务失败、并发修改、迁移中断、错误版本写入拒绝、空档案／回收站／方案、完整备份恢复及大量合成记录。通过后才将新存储设为真实默认后端。

## 阶段四：安装、签名、更新与发行

本地功能和迁移验收完成后，单独确认安装方式、目标 Windows 版本／架构、离线需求、签名证书和发行渠道。随后创建安装／卸载包，核验签名、包校验值、干净机器安装、升级和卸载的数据保留行为。自动更新还需签名验证、失败恢复及程序／数据兼容判断，不能只替换应用文件。

本轮用户授权覆盖代码修改与本地验证。安装新工具或运行时、修改系统安全设置、合并远端分支、创建 Release、部署、签名证书配置和自动更新发布，都未在本轮执行。需要实际实施时，先交付具体待安装项目或待发布产物与验证结果，再按授权范围继续。

## 实施顺序与交付边界

当前轮次交付源代码、可审查的本地提交、代码备份、合成数据验证结果及本方案。下一轮先完成阶段一合同并选择阶段二原型；同一阶段通过相应验收后才进入下一阶段。阶段三真实迁移依赖用户本机完整数据备份，阶段四发行依赖明确发布授权。

代码基线和当前回退方法见 [本地基线记录](https://github.com/ZekeNiu/MotionBench/blob/review-v2.17.2-local-20261010-r2/docs/local-baseline-20261010.md)，现有模块结构见 [架构说明](https://github.com/ZekeNiu/MotionBench/blob/review-v2.17.2-local-20261010-r2/docs/architecture.md)。本文的验收条件是后续进入下一阶段的标准，不表示已完成 Windows 应用、真实数据备份或迁移。
